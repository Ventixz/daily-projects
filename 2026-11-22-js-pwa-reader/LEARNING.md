## What it is

**Offline Reader** is a small blog reader that installs like an app and keeps working with no network:

- **Part 1, offline-first:** a service worker precaches the app shell (HTML, CSS, JS, icon) and serves it
  cache-first. Each article you open is cached *stale-while-revalidate*. Opening an article offline that
  you have never seen shows an offline page instead of the browser's error screen.
- **Part 2, instant loading:** the home page draws the article list it saved in **IndexedDB** last time,
  with no network wait. Then it fetches the live list, draws again, and saves it. Offline, the saved list
  stays up with "You are offline. Showing the copy saved 5 min ago."
- **Part 3, push:** readers can subscribe to notifications. Publishing an article sends a **Web Push**
  message to every subscriber. The message is encrypted with RFC 8291 and signed with VAPID (RFC 8292),
  using only `node:crypto`. Subscriptions that the push service reports as gone (404 or 410) are deleted.

There are no dependencies. The server is `node:http` (about 300 lines). The client is plain JavaScript with
no build step. Even the PNG icons are generated by a ~100-line script that writes the PNG format by hand.

## Run it

```
npm start                     # http://localhost:8080 (Node 20+)
ADMIN_TOKEN=<printed token> npm run publish-article -- "Title" "Summary" "Paragraph one" "Paragraph two"
npm test                      # 50 unit + HTTP tests, no browser needed
npm run test:e2e              # real Chromium via Playwright (skipped if Playwright is missing)
```

On Windows 11 / PowerShell: `winget install OpenJS.NodeJS.LTS`, then the same commands. For the env var,
use `$env:ADMIN_TOKEN="..."; npm run publish-article -- ...`.

Service workers need a secure context. `localhost` and `127.0.0.1` count as secure, so local development
needs no TLS. In production, serve over HTTPS. Push only reaches real browsers when the server can reach
their vendor's push service (FCM, Mozilla autopush, WNS or Apple).

**Tests (51):**

- **18 strategy tests** run `public/sw-strategies.js` in Node with a fake Cache and a fake fetch. They
  cover routing, cache-first, stale-while-revalidate (cached, uncached, offline, 404 must not overwrite,
  fetch that throws synchronously), old-cache cleanup, and push-payload hardening.
- **13 Web Push tests** check the encrypted body and **every intermediate key** against **RFC 8291
  Appendix A**. They also cover a round trip through a receiver written separately (the browser's side),
  tamper detection, the 4096-byte limit at exactly 3993 bytes of plaintext, keys that are not on the curve,
  and VAPID JWTs that verify with ES256 (while a forged key does not).
- **19 HTTP tests** start the real server and a **local fake push service**. The fake service checks the
  VAPID signature and decrypts each message, the way a browser vendor and a browser would. Publishing to
  4 subscribers must give 2 delivered, 1 pruned (410) and 1 kept (500 is temporary). Other tests cover
  traversal attempts, HTML escaping, the SSRF allowlist, body limits, persistence across restarts, and
  10 concurrent publishes.
- **1 end-to-end test** in Chromium: the worker installs and takes control, the list lands in IndexedDB,
  an opened article gets "Saved for offline", and a push sent over the DevTools protocol shows a toast.
  Then the server is **shut down**: the home page, the saved list and the opened article still load, and an
  unopened article shows the offline page. It passed 5 runs out of 5.

## What I learned

- **The service worker lifecycle is about never running two versions at once.** `install` precaches into a
  versioned cache (`shell-v1`). If any file fails, `addAll` rejects and the old worker stays in charge. A
  new version then *waits*. It only activates when no tab still uses the old one, and `activate` deletes
  every cache it doesn't know. I don't call `skipWaiting()` on my own. The page shows "A new version is
  ready" and posts `SKIP_WAITING` only when the reader clicks. Then `controllerchange` reloads, but only
  after that click: `clients.claim()` also fires `controllerchange` on the *first* visit, and reloading
  then would be a pointless flash.
- **Precaching must skip the HTTP cache.** `cache.addAll(urls)` goes through the browser's HTTP cache, so a
  new worker could precache yesterday's `app.js`. Each URL is wrapped in `new Request(url, { cache:
  'reload' })`. For the same reason, `sw.js` itself is served `no-store`.
- **Pick a strategy per kind of resource, not one for the whole site.** The shell is cache-first (it only
  changes on deploy, and the cache name is the version). Articles are stale-while-revalidate (instant, at
  most one visit stale). The JSON API is not cached by the worker at all, because the page keeps it in
  IndexedDB. Caching it in both places would mean two copies that can disagree. Articles live in an
  *unversioned* cache, so shipping a new shell doesn't erase what the reader saved.
- **`waitUntil` has to be called synchronously.** Stale-while-revalidate returns the cached response at once
  while `cache.put` is still running. Unless that work is passed to `event.waitUntil`, the browser may kill
  the idle worker mid-write. `waitUntil` only works during event dispatch, so the strategy returns
  `{ response, update }` promises up front and the fetch handler passes both on at once. `update` never
  rejects, so a failed refresh can't cause an unhandled rejection.
- **A `Response` body can be read once.** Every cache write uses `response.clone()`, made *before* anything
  reads the body. Only `200 OK` non-opaque responses are cached. Caching a 500 would keep serving the
  error after the server recovered, and a test checks that a 404 doesn't overwrite a good cached article.
- **IndexedDB is a transactional database with an event API.** Two small helpers wrap a request and a
  *transaction* in promises. A write is only durable at `oncomplete`, not when `put()` succeeds. Saving the
  list is `clear()` plus `put()`s plus the `lastSynced` timestamp, all in **one** transaction. A quota error
  or a crash leaves the old list whole, and articles deleted on the server disappear. The schema can only
  change in `onupgradeneeded`. `onversionchange` closes the connection so another tab's upgrade isn't
  blocked forever.
- **`navigator.onLine` only tells you about "offline".** When it is `false` you are offline. When it is
  `true`, it only means some network interface is up: a captive portal or a dead server still says `true`.
  The e2e test showed this. Under Playwright's offline emulation, `onLine` stayed `true` in this Chromium.
  So the offline indicator also turns on when a real fetch fails.
- **Web Push encryption is ECDH + HKDF + AES-GCM, and each detail matters.** For each message: generate an
  ephemeral P-256 key pair, do ECDH with the browser's `p256dh`, then
  `PRK_key = HMAC(auth, ecdh)` → `IKM = HMAC(PRK_key, "WebPush: info\0" ‖ ua_pub ‖ as_pub ‖ 0x01)` →
  `PRK = HMAC(salt, IKM)` → a 16-byte CEK and a 12-byte nonce. Then encrypt `payload ‖ 0x02`, where 0x02
  is the last-record delimiter. The header is `salt(16) ‖ rs(4) ‖ idlen(1) ‖ as_pub(65)`. A fresh key pair
  and salt every time matter: reusing them would reuse the GCM key+nonce pair, which breaks GCM
  completely. The RFC test vector matched on the first run. It is now a regression test, along with all
  six intermediate values, so a future change shows *which* step broke.
- **The size limit comes from the framing.** The push body caps at 4096 bytes. Minus the 86-byte header,
  the 16-byte GCM tag and the 1-byte delimiter, that leaves **3993** bytes of plaintext. A test encrypts
  exactly 3993 bytes, gets a 4096-byte body, and confirms 3994 is rejected.
- **VAPID is a short JWT, and JWS signatures are not DER.** The `aud` claim is the push service's *origin*
  (not the endpoint URL), `exp` is at most 24 h away, and `sub` must be `mailto:` or `https:`. Node's
  `crypto.sign` produces DER-encoded ECDSA by default. JWS ES256 needs the raw 64-byte `r‖s`, which is
  `dsaEncoding: 'ieee-p1363'`. The VAPID key must never change: every subscription is bound to it.
- **Storing someone else's URL and POSTing to it later is SSRF.** Subscription endpoints come from the
  browser, so an attacker can send `http://169.254.169.254/...` and the server would call it on every
  publish. Endpoints must be HTTPS on a known push service host (FCM, Mozilla, WNS, Apple), with no custom
  port. Keys are checked to be a real point on the curve when someone subscribes, not when we first send.
  404 and 410 from the push service mean "gone forever", so the subscription is deleted. 5xx is temporary,
  so it is kept.
- **The push payload is untrusted in the worker, too.** `parsePushData` caps the field lengths and only
  accepts a same-origin path as the click URL. `https://evil…`, `//evil…` and `/\evil…` all become `/`.
  The e2e test pushes an off-site URL and checks the toast links to `/`. The page builds every element with
  `textContent`, never `innerHTML`, and the server escapes every article field it renders.
- **Keep the logic out of the global-heavy file.** `sw.js` depends on `self`, `caches` and `fetch`, so it
  is hard to test. The decisions live in `sw-strategies.js`, a plain script loaded by `importScripts`
  (classic workers can't use `import`). It takes a cache and a fetch function as arguments, so Node can
  test it with fakes.
